# E6-S3 — Orchestrate the claim pipeline with failure handling

**Epic:** E6 — Assessment & Decision
**Layer:** Service
**Group:** H
**Depends on:** E6-S2, E5-S1

## Description

Wire intake, document check, fraud screening, assessment, and decision into one orchestrated pipeline call, and route unexpected mid-pipeline errors to PROCESSING_FAILED instead of a raw 500, per BRD section 11 failure handling.

## Acceptance Criteria

1. Given a claim with complete documents and no fraud flag, when run_pipeline() is invoked, then it ends in exactly one terminal state among AUTO_APPROVED, MANUAL_REVIEW, REJECTED, with a matching Decision row.
2. Given a claim with incomplete documents, when run_pipeline() is invoked, then it halts at DOCS_PENDING and does not call the fraud or assessment services.
3. Given the fraud or assessment step raises an unexpected exception, when caught by the orchestrator, then the claim transitions to PROCESSING_FAILED and the error is logged as structured JSON with no PII fields, per NFR-06.
4. Given a claim in PROCESSING_FAILED, when an admin calls retry_pipeline(), then the pipeline re-runs starting from the failed step.
